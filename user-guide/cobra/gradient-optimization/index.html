    Gradient Optimization

    Gradient optimization is the continuous-parameter optimization path used by the COBRA subsystem.

    The current source provides three registered gradient optimizers:

    gd
momentum
adam

    implemented under:

    kfc_procedure/cobra/core/optimizers/gradient/
├── base.py
├── gd.py
├── momentum.py
└── adam.py

    Numerical-gradient utilities live in:

    kfc_procedure/cobra/core/optimizers/_utils.py

    The gradient family is used by:

    GradientCOBRA
MixCOBRARegressor

    when:

    opt_method="grad"

    and the selected kernel advertises:

    requires_grad = True

    What gradient optimization tunes

    The gradient subsystem minimizes a scalar objective:

    \[ \min_x f(x). \]

    In COBRA, \(x\) usually represents aggregation parameters rather than the coefficients of the original base estimators.

    Examples include:

    GradientCOBRA
    x = [bandwidth]

MixCOBRA one-parameter mode
    x = [bandwidth-like parameter]

MixCOBRA two-parameter mode
    x = [alpha, beta]

    The objective itself is the cross-validation loss produced by the fitted COBRA aggregation pipeline.

    Position in the pipeline

    flowchart LR
    X["Parameter vector"]
    A["Adapter"]
    K["Kernel"]
    G["Aggregator"]
    L["Cross-validation loss"]
    N["Numerical gradient"]
    O["Gradient optimizer"]

    X --> A --> K --> G --> L
    L --> N
    N --> O
    O --> X

    The optimizer does not directly train:

    base estimators
distance models
kernel models

    Instead, it repeatedly evaluates how changing the adapter parameters affects the cross-validation objective.

    Registered gradient optimizers

    Registry name Class Update strategy
    gd GradientDescentOptimizer plain gradient descent
    momentum MomentumOptimizer gradient descent with velocity
    adam AdamOptimizer adaptive first/second moments

    All three are registered with categories:

    optimizer
gradient

    through:

    OptimizerFactory

    BaseGradientOptimizer

    All gradient implementations inherit:

    BaseGradientOptimizer

    which provides:

    gradient calculation
learning-rate schedules
parameter initialization
main optimization loop
early stopping
history tracking

    Subclasses only need to implement:

    step(
    x,
    lr,
    grad,
    state,
)

    Constructor

    The current base constructor is:

    BaseGradientOptimizer(
    learning_rate=0.01,
    max_iter=300,
    tol=1e-7,
    speed="constant",
    gradient_method="central",
    eps=1e-7,
    n_tries=5,
    init_range=(1e-4, 3.0),
    show_process=True,
    **kwargs,
)

    Core parameters

    Parameter Current default Purpose
    learning_rate 0.01 initial learning-rate scale
    max_iter 300 maximum optimizer iterations
    tol 1e-7 gradient-norm stopping threshold
    speed "constant" learning-rate schedule
    gradient_method "central" numerical-gradient method
    eps 1e-7 finite-difference step
    n_tries 5 initialization candidates
    init_range (1e-4, 3.0) initialization interval
    show_process True progress display

    Gradient computation

    The base optimizer calls:

    compute_gradient(
    objective=objective,
    params=params,
    gradient=grad_fn,
    method=self.gradient_method,
    eps=self.eps,
)

    If:

    grad_fn

    is supplied, it overrides numerical differentiation.

    Otherwise, the requested numerical-gradient method is used.

    Supported numerical-gradient methods

    The current dispatcher supports:

    central
forward
spsa
complex
parallel

    through:

    GRADIENT_METHODS

    Central difference

    The default method is:

    central

    For parameter coordinate \(i\):

    \[ g_i = \frac{ f(x+\varepsilon e_i) - f(x-\varepsilon e_i) }{ 2\varepsilon }. \]

    The source temporarily perturbs one coordinate at a time.

    Implementation concept:

    p[i] = original + eps
f_plus = objective(p)

p[i] = original - eps
f_minus = objective(p)

grad[i] = (
    f_plus
    -
    f_minus
) / (
    2 * eps
)

    Central-difference cost

    For a parameter vector of dimension:

    \[ d, \]

    one gradient calculation requires approximately:

    \[ 2d \]

    objective evaluations.

    Since a COBRA objective itself runs cross-validation, numerical gradients can be computationally expensive even for low-dimensional parameter vectors.

    Forward difference

    The source also supports:

    forward

    with:

    \[ g_i = \frac{ f(x+\varepsilon e_i) - f(x) }{ \varepsilon }. \]

    The implementation evaluates:

    f0 = objective(p)

    once, then one positive perturbation per dimension.

    Approximate cost:

    \[ d+1 \]

    objective calls per gradient evaluation.

    SPSA

    The method:

    spsa

    uses Simultaneous Perturbation Stochastic Approximation.

    The source samples:

    delta = np.random.choice(
    [-1.0, 1.0],
    size=p.shape,
)

    then computes:

    \[ g \approx \frac{ f(x+\varepsilon\Delta) - f(x-\varepsilon\Delta) }{ 2\varepsilon\Delta }. \]

    SPSA cost

    Only two objective evaluations are required regardless of parameter dimension:

    f(x + eps * delta)
f(x - eps * delta)

    This can make SPSA attractive for higher-dimensional black-box objectives.

    SPSA reproducibility caveat

    The current helper uses:

    np.random.choice(...)

    from NumPy's global random state.

    It does not accept:

    random_state

    and does not use the COBRA estimator's seed.

    Current source behavior

    Selecting:

    gradient_method="spsa"

    introduces stochastic perturbations whose sequence is not controlled by the normal estimator random_state parameter.

    Complex-step gradient

    The method:

    complex

    uses:

    \[ g_i = \frac{ \operatorname{Im} f(x+i\varepsilon e_i) }{ \varepsilon }. \]

    The source default inside the standalone function is:

    eps=1e-20

    Important dispatcher detail

    BaseGradientOptimizer passes:

    self.eps

    into:

    compute_gradient()

    and its default is:

    1e-7.

    Therefore when complex-step differentiation is selected through the optimizer, the effective epsilon is normally:

    1e-7

    unless you explicitly configure another value.

    The standalone helper's own:

    1e-20

    default is bypassed because compute_gradient() supplies the optimizer epsilon.

    Complex compatibility

    The objective must support complex-valued parameter perturbations.

    The source does not test that compatibility before running.

    If downstream code discards imaginary components or rejects complex arrays, the method may not produce a meaningful gradient.

    Parallel central difference

    The method:

    parallel

    uses the same central-difference formula as the default method but evaluates coordinates with:

    joblib.Parallel

    and:

    delayed(...)

    Worker count

    compute_gradient() has:

    n_jobs=None

    and, for parallel mode, maps that to:

    n_jobs=-1

    unless a value is explicitly provided.

    However, BaseGradientOptimizer.gradient() currently calls compute_gradient() without passing an n_jobs argument.

    Therefore the standard optimizer path uses:

    all available workers

    for the parallel gradient helper.

    Unknown gradient methods

    If the method name is not one of:

    central
forward
spsa
complex
parallel

    the dispatcher raises:

    ValueError:
Unknown method '...'. Available: [...]

    Analytical gradients

    The optimization API supports:

    grad_fn=

    in:

    BaseGradientOptimizer.optimize()

    When present:

    compute_gradient()

    returns:

    np.asarray(
    gradient(params),
    dtype=float,
)

    and skips numerical differentiation.

    High-level COBRA usage

    The current GradientCOBRA and MixCOBRA optimization paths call the optimizer without supplying a custom:

    grad_fn

    so they use numerical gradients.

    Analytical gradients are available as a lower-level optimizer feature rather than a high-level estimator feature in the current source.

    Initialization

    When:

    init_param is None

    the base optimizer runs:

    _initialize(
    objective,
    dim=1,
)

    Initialization grid

    The source builds:

    grid = np.linspace(
    low,
    high,
    n_tries,
)

    from:

    init_range

    then constructs:

    candidates = np.array([
    np.full(
        dim,
        g,
    )
    for g in grid
])

    and chooses the candidate with the lowest objective score.

    Initialization limitation

    Inside:

    optimize()

    the source always calls:

    _initialize(
    objective,
    dim=1,
)

    when init_param is absent.

    So the automatic initialization path is effectively one-dimensional from this entry point.

    For multi-parameter optimization, a caller should provide an explicit init_param.

    The high-level MixCOBRA source does exactly that.

    COBRA initial parameters

    GradientCOBRA uses:

    init_param=np.array([
    1.0
])

    for gradient mode.

    MixCOBRA one-parameter mode uses:

    np.array([
    1.0
])

    and two-parameter mode uses:

    np.array([
    1.0,
    1.0,
])

    Therefore the internal automatic initialization search is normally bypassed in the main COBRA integrations.

    Initial gradient scaling

    After choosing x, the optimizer computes:

    grad = self.gradient(
    objective,
    x,
    grad_fn,
)

    Then:

    r0 = self.learning_rate / (
    np.linalg.norm(
        grad
    )
    +
    1e-12
)

    This is an important implementation detail.

    The value configured as:

    learning_rate

    is divided by the initial gradient norm before the learning-rate schedule is applied.

    Effective first step scale

    For constant schedule:

    \[ r_0 = \frac{ \eta }{ \|\nabla f(x_0)\|+10^{-12} }. \]

    So the first step size is normalized by the initial gradient magnitude.

    The optimizer does not directly use:

    learning_rate

    as the first raw multiplier.

    Learning-rate schedules

    The source supports:

    constant
linear
log
sqrt_root
quad
exp

    through:

    _rate(
    t,
    r0,
)

    Current formulas

    The source dictionary is:

    {
    "constant": lambda x, y: y,
    "linear": lambda x, y: x * y,
    "log": lambda x, y: np.log(1 + x) * y,
    "sqrt_root": lambda x, y: np.sqrt(1 + x) * y,
    "quad": lambda x, y: (1 + x**2) * y,
    "exp": lambda x, y: np.exp(x) * y,
}

    where:

    x = iteration index t
y = r0

    Important schedule behavior

    Several names may sound like decay schedules, but the current formulas do not decay.

    For example:

    linear
    lr_t = t * r0

log
    lr_t = log(1+t) * r0

sqrt_root
    lr_t = sqrt(1+t) * r0

quad
    lr_t = (1+t²) * r0

exp
    lr_t = exp(t) * r0

    These increase with iteration.

    linear starts at zero

    At:

    t = 0

    the linear schedule returns:

    \[ 0\times r_0 = 0. \]

    So the first update under:

    speed="linear"

    does not move the parameters.

    Exponential growth

    With:

    speed="exp"

    the learning rate becomes:

    \[ e^t r_0. \]

    This can grow extremely quickly.

    The current source does not cap or clip the scheduled learning rate.

    Current implementation

    The non-constant schedules are increasing functions as implemented.

    Do not assume names such as linear, log, or sqrt_root mean learning rate decay.

    Unknown schedule names

    The source uses:

    schedules.get(
    self.speed,
    schedules["constant"],
)

    Therefore an unknown:

    speed

    does not raise an error.

    It silently uses:

    constant

    behavior.

    Main optimization loop

    After initialization, the optimizer stores:

    best_x = x.copy()

best_score = objective(
    x
)

    Then it runs up to:

    max_iter

    iterations.

    For iteration t:

    1. compute scheduled learning rate
2. call subclass step()
3. repair NaN parameter vectors
4. compute new gradient
5. evaluate new objective
6. update best solution
7. check gradient-norm stopping
8. optionally shrink r0 after gradient sign changes
9. record history

    NaN parameter repair

    After the subclass update:

    x_new, state = self.step(
    x,
    lr_t,
    grad,
    state,
)

    the source checks:

    if np.any(
    np.isnan(
        x_new
    )
):
    x_new = x * 0.95

    So if any coordinate becomes NaN, the entire new parameter vector is replaced by:

    \[ 0.95x. \]

    Infinite values are not repaired

    The check is specifically:

    np.isnan(
    x_new
)

    The source does not separately repair:

    +Inf
-Inf

    parameter values.

    Best-solution tracking

    After evaluating:

    score = objective(
    x_new
)

    the source updates:

    if score < best_score:
    best_score = score
    best_x = x_new.copy()

    The optimizer returns the best point encountered, not necessarily the final iteration point.

    Early stopping

    The gradient is recomputed at:

    x_new

    and stopping occurs when:

    \[ \|\nabla f(x_{\text{new}})\| < \text{tol}. \]

    The exact check is:

    if np.linalg.norm(
    grad_new
) < self.tol:
    x = x_new
    break

    History omission on early stopping

    This stopping check happens before the history entry is appended.

    Therefore the final converged step is not added to:

    history

    when optimization terminates through this gradient-norm condition.

    The score can still update:

    best_score
best_x

    before the break.

    Gradient-sign adjustment

    After at least four previous iterations:

    if (
    t > 3
    and np.any(
        np.sign(
            grad_new
        )
        !=
        np.sign(
            prev_grad
        )
    )
):
    r0 *= 0.99

    So if any gradient coordinate changes sign, the base learning-rate scale is reduced by:

    1%

    Sign comparison detail

    The comparison is between:

    grad_new

    and:

    prev_grad

    not directly between grad_new and the current grad.

    At the end of each completed iteration:

    prev_grad = grad_new.copy()
grad = grad_new.copy()

    so after normal completed iterations those values become identical for the next loop.

    This means the effective comparison is against the prior stored gradient.

    Optimization history

    A completed iteration appends:

    {
    "iter": t + 1,
    "x": x.copy(),
    "score": score,
    "grad": grad,
    "grad_norm": float(
        np.linalg.norm(
            grad
        )
    ),
    "lr": lr_t,
}

    History fields

    Field Meaning
    iter one-based iteration number
    x parameter vector after update
    score objective value at that vector
    grad gradient at that vector
    grad_norm Euclidean gradient norm
    lr scheduled step multiplier used for the update

    History is not total objective-call history

    A finite-difference gradient can call the objective multiple times per iteration.

    Those internal calls are not recorded as history entries.

    The following are also evaluated outside normal history rows:

    initial gradient
initial best-score calculation
terminating early-stop step
initialization candidate search, when used

    So:

    len(
    result["history"]
)

    is the number of recorded optimizer iterations, not the total number of objective evaluations.

    Progress display

    When:

    show_process=True

    the optimizer wraps the iteration range in:

    tqdm(
    range(
        max_iter
    ),
    desc="GD",
    leave=True,
)

    This description remains:

    GD

    even for:

    MomentumOptimizer
AdamOptimizer

    because the progress loop is implemented in the shared base class.

    Progress text

    After a completed iteration, the description is changed to:

    iter=N | score=... | grad_norm=...

    Gradient Descent

    The simplest registered optimizer is:

    GradientDescentOptimizer

    under:

    gd

    Its update rule is:

    \[ x_{t+1} = x_t - \eta_tg_t. \]

    The implementation is exactly:

    x_new = (
    x
    -
    lr
    *
    grad
)

    The state dictionary is unchanged.

    Direct use

    import numpy as np

from kfc_procedure.cobra.core.optimizers import (
    GradientDescentOptimizer,
)


def objective(
    params,
):
    x = params[0]

    return (
        x - 2.0
    ) ** 2


optimizer = GradientDescentOptimizer(
    learning_rate=0.1,
    max_iter=100,
    show_process=False,
)

result = optimizer.optimize(
    objective,
    init_param=np.array([
        1.0
    ]),
)

print(
    result["x"]
)

print(
    result["score"]
)

    Momentum

    MomentumOptimizer is registered as:

    momentum

    and adds:

    momentum=0.9

    to the base optimizer parameters.

    Momentum state

    On the first step:

    state["v"] = np.zeros_like(
    x
)

    The state stores one velocity vector:

    v

    Momentum update

    The source computes:

    \[ v_t = \mu v_{t-1} - \eta_tg_t \]

    then:

    \[ x_{t+1} = x_t+v_t. \]

    Implementation:

    v = (
    self.momentum
    *
    v
    -
    lr
    *
    grad
)

state["v"] = v

x_new = x + v

    Configure momentum

    optimizer = MomentumOptimizer(
    momentum=0.95,
    learning_rate=0.05,
    max_iter=200,
    show_process=False,
)

    The current constructor does not validate that:

    0 <= momentum < 1

    or any other interval.

    The supplied value is used directly.

    Adam

    AdamOptimizer is registered as:

    adam

    and adds:

    beta1=0.9
beta2=0.999

    to the base configuration.

    Adam state

    On first use, the source creates:

    state["m"] = np.zeros_like(
    x
)

state["v"] = np.zeros_like(
    x
)

state["t"] = 0

    The state therefore tracks:

    m
    first moment

v
    second moment

t
    optimizer timestep

    Adam moment updates

    The source computes:

    \[ m_t = \beta_1m_{t-1} + (1-\beta_1)g_t \]

    and:

    \[ v_t = \beta_2v_{t-1} + (1-\beta_2)g_t^2. \]

    Bias correction

    The implementation applies:

    \[ \hat m_t = \frac{ m_t }{ 1-\beta_1^t } \]

    and:

    \[ \hat v_t = \frac{ v_t }{ 1-\beta_2^t }. \]

    Adam update

    The source uses:

    \[ x_{t+1} = x_t - \eta_t \frac{ \hat m_t }{ \sqrt{\hat v_t} + 10^{-8} }. \]

    The stabilizer:

    1e-8

    is hard-coded inside:

    AdamOptimizer.step()

    No configurable Adam epsilon

    The class docstring mentions an epsilon numerical stability constant, but the constructor is:

    AdamOptimizer(
    beta1=0.9,
    beta2=0.999,
    **kwargs,
)

    There is no explicit:

    epsilon=

    parameter.

    The update always uses:

    1e-8

    in the current source.

    Documentation/source mismatch

    The class documentation mentions an Adam epsilon parameter, but the current constructor does not expose one.

    Configure Adam

    optimizer = AdamOptimizer(
    beta1=0.9,
    beta2=0.999,
    learning_rate=0.05,
    max_iter=200,
    gradient_method="central",
    show_process=False,
)

    The current source does not explicitly validate the ranges of:

    beta1
beta2.

    Kernel compatibility

    GradientCOBRA and MixCOBRA do not blindly use gradient optimization.

    Before choosing the optimizer family, they check:

    kernel_.requires_grad

    Gradient-compatible built-in kernels

    The current continuous kernels advertise:

    requires_grad = True

    including:

    rbf / radial / gaussian
exponential
reverse_cosh
cauchy

    Non-gradient kernels

    The current compact/discrete kernels advertise:

    requires_grad = False

    including:

    epanechnikov
biweight
triweight
triangular
naive
cobra

    Automatic fallback to grid search

    If:

    opt_method="grad"

    but:

    kernel_.requires_grad == False

    both GradientCOBRA and MixCOBRA change the local effective method to:

    grid

    before optimizer resolution.

    So:

    GradientCOBRA(
    kernel="cobra",
    opt_method="grad",
    optimizer="adam",
)

    does not continue with Adam under the normal source path.

    It falls back to grid-family optimization.

    Category validation

    For GradientCOBRA and MixCOBRA, effective:

    grad

    mode requires:

    OptimizerFactory.supports(
    optimizer,
    category="gradient",
)

    So:

    optimizer="grid"
opt_method="grad"

    is rejected when the effective method remains gradient-based.

    Likewise, grid mode requires the:

    search

    category.

    GradientCOBRA configuration

    The relevant constructor parameters include:

    optimizer="grid"
optimizer_params=None
opt_method="grid"
learning_rate=0.1
max_iter=300

    To enable gradient optimization:

    from kfc_procedure.cobra import (
    GradientCOBRA,
)

model = GradientCOBRA(
    optimizer="adam",
    opt_method="grad",
    learning_rate=0.05,
    max_iter=200,
)

    GradientCOBRA optimizer parameters

    The source copies:

    optimizer_params

    then, in gradient mode, updates:

    {
    "learning_rate": self.learning_rate,
    "max_iter": self.max_iter,
}

    before creating the optimizer.

    Therefore top-level:

    learning_rate
max_iter

    take precedence over same-named values previously placed in optimizer_params.

    Additional GradientCOBRA optimizer settings

    Use optimizer_params for options such as:

    optimizer_params={
    "tol": 1e-6,
    "gradient_method": "forward",
    "eps": 1e-6,
    "speed": "constant",
    "show_process": False,
    "beta1": 0.9,
    "beta2": 0.999,
}

    Parameters irrelevant to a given subclass may be absorbed by **kwargs depending on the constructor path.

    GradientCOBRA starting point

    The current gradient path calls the optimizer with:

    init_param=np.array([
    1.0
])

    so bandwidth optimization starts from:

    \[ h_0=1. \]

    GradientCOBRA result

    After optimization:

    self.bandwidth_ = float(
    np.atleast_1d(
        result["x"]
    )[0]
)

    and the source stores:

    self.optimization_outputs_ = {
    "method": method,
    "optimizer": optimizer,
    "bandwidth": self.bandwidth_,
    "score": result["score"],
    "history": history_df,
    "evaluations": len(
        result["history"]
    ),
}

    GradientCOBRA records effective method

    The stored:

    optimization_outputs_[
    "method"
]

    uses the local effective method.

    Therefore if the kernel forces a fallback from:

    grad

    to:

    grid,

    GradientCOBRA reports:

    grid.

    optimizer="grid"

    from kfc_procedure.cobra import (

    With:

    one_parameter=False

    the optimizer starts from:

    np.array([
    1.0,

])

    representing:

    \[ (\alpha,\beta) = (1,1). \]

    MixCOBRA result

    The optimization output stores:

    {
    "method": self.opt_method,
    "score": result["score"],
    "history": history_df,
    "evaluations": len(
        result["history"]
    ),
    "params": result["x"],
}

    MixCOBRA reporting caveat

    The current source stores:

    self.opt_method

    rather than the local effective method after kernel fallback.

    Therefore a model configured with:

    opt_method="grad"

    can still report:

    grad

    even if a non-gradient kernel caused the actual path to use grid optimization.

    This differs from GradientCOBRA.

    No positivity constraints

    The base gradient optimizer performs ordinary unconstrained vector updates.

    There is no generic source-level projection such as:

    x_new = np.maximum(
    x_new,
    0.0,
)

    or clipping to a configured interval.

    Therefore parameters such as:

    bandwidth
alpha
beta

    can become negative during gradient optimization.

    Why this matters

    For the one-parameter adapter:

    \[ D' = hD. \]

    A negative:

    \[ h \]

    turns non-negative distances into negative adapted values.

    With the default RBF kernel:

    \[ K=e^{-D'}, \]

    this can produce weights larger than one:

    \[ e^{-hD} > 1 \]

    when:

    \[ h<0. \]

    The current optimizer does not prevent this.

    Current gradient path is unconstrained

    Grid search uses an explicitly positive default candidate range 0.001 to 10.0.

    Gradient optimization is not restricted to that interval.

    No general parameter clipping

    The same applies to MixCOBRA:

    \[ D_{\text{mix}} = \alpha D_X + \beta D_Y. \]

    Gradient mode can produce:

    negative alpha
negative beta

    because no projection step is implemented.

    The source leaves those parameter semantics to the objective and optimizer trajectory.

    Objective smoothness

    The gradient path uses finite differences over the full cross-validation objective.

    That objective contains several components:

    adapter
kernel
aggregator
loss
fold averaging

    Whether the numerical gradient behaves smoothly depends on the entire composed pipeline.

    Hard operations and gradient compatibility

    The high-level source uses:

    kernel_.requires_grad

    as its explicit compatibility gate.

    However, this flag describes the kernel only.

    Other parts of the objective can still contain non-smooth behavior, for example:

    classification argmax
zero-weight fallbacks
piecewise losses

    The current optimizer does not perform symbolic differentiability analysis of the whole objective.

    Gradient methods are black-box approximations

    The finite-difference helpers only need:

    objective(
    params
) -> scalar

    They do not require access to analytical derivatives of:

    kernel
aggregator
loss

    This makes the gradient subsystem effectively a black-box numerical optimizer.

    Central difference with COBRA CV

    For one GradientCOBRA bandwidth:

    \[ h, \]

    central difference approximates:

    \[ J'(h) \approx \frac{ J(h+\varepsilon) - J(h-\varepsilon) }{ 2\varepsilon }, \]

    where each:

    \[ J(\cdot) \]

    is itself a full mean cross-validation loss.

    Two-parameter central difference

    For MixCOBRA:

    \[ x = (\alpha,\beta), \]

    central difference requires approximately four full objective evaluations per gradient:

    \[ J(\alpha+\varepsilon,\beta), \]
    \[ J(\alpha-\varepsilon,\beta), \]
    \[ J(\alpha,\beta+\varepsilon), \]
    \[ J(\alpha,\beta-\varepsilon). \]

    The optimizer then separately evaluates the objective at the new parameter vector.

    eps sensitivity

    The default finite-difference step is:

    1e-7.

    If the objective changes very little at that scale, numerical cancellation can make the estimated gradient noisy.

    If the objective has abrupt changes, a tiny epsilon can sample two points on different sides of a discontinuity.

    The current source exposes:

    eps

    through optimizer_params, so it can be tuned manually.

    Example with forward differences

    model = GradientCOBRA(
    optimizer="gd",
    opt_method="grad",
    learning_rate=0.05,
    optimizer_params={
        "gradient_method": "forward",
        "eps": 1e-5,
        "show_process": False,
    },
)

    Example with SPSA

    model = MixCOBRARegressor(
    optimizer="adam",
    opt_method="grad",
    optimizer_params={
        "gradient_method": "spsa",
        "eps": 1e-4,
        "show_process": False,
    },
)

    Remember that the current SPSA helper is not seeded from:

    model.random_state.

    Example with parallel central differences

    model = MixCOBRARegressor(
    optimizer="adam",
    opt_method="grad",
    optimizer_params={
        "gradient_method": "parallel",
        "show_process": False,
    },

    The standard BaseGradientOptimizer.gradient() call does not expose a custom n_jobs, so the parallel helper uses its fallback worker count:

    -1.

    Custom gradient optimizer

    To implement a new update rule, subclass:

    BaseGradientOptimizer

    and implement:

    step()

    Example:

    import numpy as np

from kfc_procedure.cobra.core.optimizers import (
    OptimizerFactory,
)

from kfc_procedure.cobra.core.optimizers.gradient import (
    BaseGradientOptimizer,
)


@OptimizerFactory.register(
    "sign_gd",
    categories={
        "optimizer",
        "gradient",
    },
)
class SignGradientOptimizer(
    BaseGradientOptimizer
):

    def step(
        self,
        x,
        lr,
        grad,
        state,
    ):
        x_new = (
            x
            -
            lr
            *
            np.sign(
                grad
            )
        )

        return (
            x_new,
            state,
        )

    This automatically inherits:

    gradient estimation
learning-rate schedules
early stopping
history
initialization
progress display

    from the base class.

    Custom optimizer result contract

    The inherited optimize() method returns:

    {
    "x": best_x,
    "score": best_score,
    "history": history,
}

    which matches the result contract expected by GradientCOBRA and MixCOBRA.

    Mental model

    Gradient optimization treats the complete COBRA cross-validation pipeline as a black-box scalar function and numerically follows parameter directions that reduce that loss.

    For GradientCOBRA:

    \[ \boxed{ h \rightarrow J(h) \rightarrow \frac{dJ}{dh} \rightarrow h_{\text{new}} } \]

    For two-parameter MixCOBRA:

    \[ \boxed{ (\alpha,\beta) \rightarrow J(\alpha,\beta) \rightarrow \nabla J \rightarrow (\alpha,\beta)_{\text{new}} } \]

    The current implementation provides GD, Momentum, and Adam update rules over the same shared numerical-gradient and stopping machinery.
